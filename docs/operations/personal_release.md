## 授权与版本

提交、推送、tag/Release/镜像发布、生产部署均须用户明确授权。直接使用用户指定的当前 main，不自行创建分支，不提交本地计划、`SYNC.md` 或秘密。不要调用 Plus 的 `push-cli`、`release-cli` 或旧迁移工具。

版本使用递增的三段数字 `X.Y.Z`，与上游版本序列分开管理。先把版本写入 `backend/cmd/server/VERSION` 并提交，再创建指向该确切 SHA 的 annotated tag `vX.Y.Z`。tag body 必须包含中文变更说明、上游基线、兼容性、迁移、已知问题和回退约束。禁止移动已发布 tag 或复用版本。镜像 tag 不带 v，不发布可漂移的 latest 作为生产更新依据。

## 发版前验证

提交发布改动前，根据实际变更列出验证范围，记录通过的命令、源码/依赖状态和结果。修改数据库访问、事务并发、共享测试夹具、清理逻辑或 outbox 时，必须在本地运行完整受影响的集成测试包，覆盖新增用例与既有套件共同运行的情况；只用 `-run` 验证新增用例不能作为发版依据。例如仓储相关改动运行：

```bash
# 从仓库根执行；Docker 连接使用当前环境已验证的配置。
(cd backend && go test -tags=integration ./internal/repository)
```

测试隔离要求见 [开发流程的验证策略](development_workflow.md#验证策略)。前端、lint、迁移和安全检查按变更补齐；若源码、依赖或相关运行环境未变，复用已经通过的有效验证结果，不因创建 tag 再完整执行一遍本地应用测试。纯文档变更运行结构与差异检查。

CI 失败时先读取失败日志，区分源码/夹具缺陷与基础设施故障。源码缺陷修复后重新验证受影响范围，并按不可变版本规则处理新提交；不能对相同缺陷反复重跑流水线。

<a id="release_pipeline"></a>
## ARM64 流水线

1. 完成发版前验证后推送 main，CI 和 Security Scan 验证该确切 SHA。发布脚本和升级来源变更运行针对性检查；已经完成的功能验证不因创建 tag 在本地完整重跑。
2. `v*` tag 只负责调度 main 上的 Personal ARM64 Release；手动 workflow dispatch 也必须选择 main，并传入现有 tag。实际构建检出目标 tag 而不是 main 最新源码，验证 VERSION/tag/SHA 和 main 祖先关系，只允许个人仓库执行，不自动修改源码或回写版本。
3. 使用原生 ARM64 runner。Node 22、pnpm 9.15.9 容器构建一次前端，Go 1.27.0 容器只构建一次嵌入前端的 Linux ARM64 程序；具体工具链以 workflow 和 `backend/go.mod` 为准。
4. 缓存包含 pnpm store、Go modules、Go build 和运行时镜像层，统一保存在 main 的 Actions 缓存作用域。GitHub 不允许不同 tag 直接互相恢复缓存，只设置 restore-keys 不足以跨 tag 复用，因此不能把实际构建重新移回 tag push job。依赖缓存键包含工具链、manifest/lock 哈希；同依赖代内源码变化复用编译缓存，不跨依赖代恢复。冷缓存首次发布会明显慢于后续发布。
5. `Dockerfile.goreleaser` 仅包装预编译程序和运行时资源，不再次编译，不执行 GoReleaser 的跨平台矩阵。运行容器验证程序、ARM64 架构、PostgreSQL dump/psql 工具。
6. 构建和 main 验证并行，发布前必须确认同 SHA 的 CI 与 Security Scan 成功。失败不发布，不通过跳过检查或现场编译绕过；tag 不重复触发这两个完整工作流。
7. 只发布 `ghcr.io/tiantianr/tokenrouter:X.Y.Z` 与 GitHub Release。Release 附带 `release-manifest.json`，绑定版本、完整 SHA、平台、构建类型和镜像 digest；镜像必须公开且可由生产主机拉取。没有二进制归档、校验和安装包、amd64/macOS/Windows 或 DockerHub 产物。

首次启用 Actions 后要核对仓库权限、ARM64 runner 可用性、GHCR 包可见性和实际下载。构建失败可在相同未发布 tag 上重跑；镜像已推送但 Release 尚未建立时只允许复用 revision 完全一致的镜像。已有 Release 时停止并人工核对，不覆盖产物。

## 容量与恢复预检

先核对本次是否有迁移、是否允许在线备份与新旧实例混跑，再安排阶段顺序。允许在线升级时，CI、安全检查、ARM64 构建与通过以下预检的生产备份恢复并行推进；发布和恢复验证全部成功后才切换应用。不能为了并行跳过破坏性迁移的排空、停机或单实例执行要求。

### 容量预算

开始完整导出前记录下列信息，不沿用历史小备份的压缩率或容量假设：

| 对象 | 预检依据 |
| --- | --- |
| 生产数据库 | `pg_database_size`、大表及索引/TOAST 体积、近期增长，尤其是审计与日志数据；数据库物理大小不是 dump 或恢复峰值的严格上限。 |
| dump 与其它备份 | 最近有效备份的实际体积、时间和范围，结合当前增长预算；同时计入 Redis、应用数据和配置。缺少可靠基线时选择保守容量方案。 |
| 恢复工作区 | 完整恢复的数据、索引、WAL、临时文件及文件系统实际分配峰值，不能只按 dump 大小估算。 |
| 实际文件系统 | 核对路径解析后的挂载、可用容量、inode 和配额；同一文件系统上的 dump、恢复库及临时副本必须相加，不能按不同目录重复计算可用空间。 |
| 生产余量 | 为业务增长、WAL、应用镜像拉取及运行保留明确余量，事先设置监测与中止条件。 |

空间不足时先确定有足够容量的持久存储和恢复位置，再启动导出。不得先写满根分区再迁移文件，也不能通过省略大表、删除生产审计数据或有效备份来满足本次预算。独立磁盘的位置和可用容量每次重新核对，不把某个历史目录固定为始终可用的资源。

内存盘仅作为预检通过的临时中转方案：同时核对 tmpfs 容量、可用内存、容器内存限制及生产峰值余量，事先确定文件切换和持久化阶段。不能把手动暂停后台进程、临时移动仍在写入的文件作为常规发布流程。部署前备份必须写回持久存储、完成落盘并再次核对校验和；仅存在于内存盘或仍指向它的链接不算备份就绪。

### 恢复环境冒烟

优先复用已审查、已验证且支持本次参数的维护入口。已有一次性脚本必须先核对版本、路径、镜像、凭据读取边界和恢复状态，不能只替换版本号就当作通用工具。没有适用入口时，先准备可审查的分阶段脚本，做语法、参数和轻量冒烟检查，再开始长时间任务；长脚本通过文件传输执行，避免多层命令字符串转义。

使用本次实际 PostgreSQL 镜像、挂载布局和资源限制，先启动一个无生产连接、无宿主端口的隔离空库。等待初始化完成后的最终服务可用，对目标数据库执行连接、建临时表、写入、查询和清理检查；`pg_isready` 成功本身不能证明目标库和写入权限正确。

PostgreSQL 18 的挂载父目录与实际 `PGDATA` 需分别核对。入口脚本会降权到 `postgres` 用户，不能把 root 拥有的挂载父目录保留为 `0700` 后就认为容器可写。父目录可由实际数据库用户拥有，或设置为可遍历的权限；实际 `PGDATA` 仍保持私有权限。`umask 077` 会影响创建目录的最终模式，必须检查实际权限、属主及降权后的访问能力，不能只检查脚本传入的 mode。

启动失败先保存容器日志、退出码、实际用户、目录权限和挂载信息，再清理临时容器。先查 Unix 权限与路径，再依据拒绝日志检查 ACL/SELinux；不得仅凭 `Permission denied` 就归因 SELinux 或放宽全局权限。空库冒烟失败必须先修复，不能等完整 dump 导出后再测试恢复容器能否启动。

## ID3 部署

当前业务使用 `/opt/tokenrouter/compose.yml` 的 TokenRouter 应用、独立 PostgreSQL 和 Redis；旧 Plus 服务不是更新目标。每次先核对实际容器、镜像、端口、持久挂载和依赖状态，不沿用历史容器 IP，不输出完整环境或凭据。通过已配置的 MaidKit ID3 连接执行维护，不把生产密钥写入仓库。

1. 记录当前镜像、Compose、依赖容器 ID，完成容量与恢复环境预检。Release 就绪后读取 manifest，核对 tag SHA、OCI revision、ARM64、公开拉取和 digest；该核验与备份可分别推进。
2. 在选定的专用备份目录创建完整 PostgreSQL dump，保存 Compose、私有环境和应用数据。在线导出与预期计数、关键数据摘要必须来自同一一致快照，避免业务继续写入造成误报。核对 Redis 持久化，并保存业务需要的 RDB/AOF 或一致快照；外部对象存储另行盘点。备份权限限定运维用户，不能输出内容。
3. 将 dump 恢复到通过冒烟的隔离环境；完整恢复须正常退出，逐表核对导出快照的计数，并核对迁移和关键业务数据摘要，再删除恢复验证资源。检查持久备份文件及校验和。文件存在、能列出归档目录或空库启动成功都不能代替真实恢复。
4. 确认同 SHA 发布成功、备份持久化与恢复验证均通过后，拉取固定版本与 digest，更新应用镜像引用。只重建应用，不重建数据库/Redis，不重新初始化、重跑跨项目迁移或重置缓存。需要停机或不允许混跑的迁移按专题顺序排空旧实例。
5. 检查 health、域名、管理版本、迁移记录、实际镜像 SHA/digest、账号与用户数据。按 [真实客户端 IP 验收](edge_security.md#client_ip_resolution) 比对公网探针的入口与应用日志，确认伪造转发头无效，并核对新用量的客户端 IP。经授权执行一次小网关请求，核对成功响应、用量和计费，不发起真实支付或批量修改账号设置。
6. 健康或关键验收失败时先停止推进，按兼容性回退旧应用镜像；保留新 schema 和账务，不自动恢复旧数据库覆盖新写入。破坏性迁移必须使用其专门恢复流程。
7. 留存备份、manifest、发布与部署状态、旧回退镜像；清理本次构建/恢复验证容器、临时资源和过时代缓存，不清理无关项目。记录哪些步骤已完成以便超时后先查状态再恢复，不盲目重复部署。

## 失败续跑与产物保留

维护入口必须分别记录预检、导出、恢复、持久化、应用切换和验收状态。阶段记录包含开始/结束时间、退出码、任务或进程标识、来源身份、实际产物位置、dump 校验和、快照验证基线及失败日志；状态原子更新，敏感信息只留在服务器受限目录。长任务后台执行并提供可查询状态，MaidKit 超时后先核对远端状态，不重复启动已有任务。

- 导出成功后保留完整 dump 及其基线。恢复容器权限、恢复验证或后续验收失败时，在同一升级窗口内核对来源、范围、恢复时点和校验和，仍合格则从失败阶段续跑；后续阶段失败本身不是重新导出的理由。
- 导出失败的文件明确标记为不完整。确认相关写入进程已退出后，定向清理本次不完整文件并重新核对实际空间；不得按目录前缀批量删除有效备份。没有通过校验的文件不能进入恢复阶段。
- 在线应用日志追加引起的归档警告可按已知日志路径单独处理，并验证归档可读；配置、业务数据读取失败或不明警告必须失败退出，不能统一忽略归档工具的非零退出码。
- 空库冒烟、全量恢复成功和备份持久化分别记账；仅当前一次通过不代表后两步完成。无新增迁移也必须完成规定的备份和恢复验证。
- 每次失败先保存证据、修正原因，再重试对应阶段。保持发布产物与备份状态独立，不因生产恢复环境故障重新构建同一镜像；也不因 CI 等待重做已验证且仍符合恢复时点要求的备份。

<a id="image_updates"></a>
## 后台更新边界

更新检查与历史 Release 来源固定为个人仓库，缓存包含仓库身份，旧上游缓存不能继续使用。个人镜像编译为 `BuildType=image`，后台提供个人 Release 与镜像信息；服务端拒绝原地更新、备份二进制回退和指定版本二进制回退，即使绕过前端直接调用 API 也不能改写镜像内程序。

日常在线升级由 1Panel/Compose 在宿主机拉取并重建应用完成。网页按钮不是 Docker 部署系统，不挂载宿主机 Docker socket，不用容器内二进制替换冒充持久镜像升级。单二进制安装器虽然指向个人源，但本发行不提供安装归档，不能宣称支持该安装路径。

## 耗时与验收记录

分别记录配置准备、本地验证、CI 等待、缓存命中/冷启动、前端编译、Go 编译、镜像包装推送、数据库导出、恢复校验、持久化和应用切换耗时，失败重跑单独计时。并行阶段的耗时不能简单相加冒充总用时，构建完成也不能表述为生产更新完成。

开始长任务前根据实际数据规模、可用空间、缓存情况和历史实测说明主要耗时环节；无可靠基线时明确待测。执行中持续报告当前阶段、已用时间和剩余阻塞，阶段失败或明显偏离预期时立即说明原因与续跑位置。加速来自限定目标、缓存、并行与消除重复工作，不来自跳过安全检查、迁移验证或备份；没有实测前不承诺整个发行的固定时限。

每次交付明确区分本地、已提交、已推送、已发布、ID3 已生效；报告完整 SHA、Release URL、版本/digest、迁移结果、业务验收和备份目录。发布变更说明放 GitHub Release，不向 README 追加每版日志。
